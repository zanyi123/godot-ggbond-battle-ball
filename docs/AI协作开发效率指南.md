# 决竞球 - AI 协作开发效率指南

> **文档定位**：基于 GitHub vibecoding 最佳实践（6 份高星仓库提炼）+ 本项目实际痛点，给出**可立即落地**的效率改进方案。
> **不是空谈方法论**，每条都对应决竞球的具体场景。
> **创建日期**：2026-06-17

---

## 一、我们的核心痛点（现状诊断）

| 症状 | 根因 | 严重度 |
|---|---|---|
| 改 AI 代码 → 你测 → 发现 bug → 反馈 → 我修 → 再测 | **没有自动验证手段**，每次都靠肉眼跑游戏 | 🔴 最高 |
| 我改完不知道对不对，必须等你反馈 | AI 行为改动**无法量化验证**（卡死/接球/抖动都是肉眼观察） | 🔴 最高 |
| 同类问题反复出现（卡线修了又漏） | **没有回归基线**，改 A 不知道有没有坏 B | 🟡 中 |
| 每个 skill 规则要手动遵守 | 规则散在脑子里，没固化成 agent 可读的约束 | 🟡 中 |
| 对话变长后上下文丢失 | 长会话没有"交接"机制，下次开聊要重新解释 | 🟢 低（已有日志） |

**一句话**：你不是设计师，被迫当了人肉 QA。这是最大瓶颈。

### 提炼出的 6 条共性原则

#### 原则1：评估先行，选最小工作流（crisxuan / agent-workflow-kit）
> **不是所有改动都要走完整流程**。先评估风险，选最小够用的流程。

决竞球映射：
- **tiny-fix**（改1行配置/数值）：改完跑语法检查即可，不用全套
- **quick-win**（改1-2个函数，如修 bug）：改→语法→单点自测
- **feature**（如 P0/P1 AI 重构）：plan→实现→review→回归验证

#### 原则2：无证据不算完成（KbWen / agentic-os）
> AI 最爱说"改完了"，但"done"必须有**可验证证据**，不能靠自报。

决竞球映射：
- ❌ 现在：我说"语法检查通过"，但其实没验证"接球率有没有回归"
- ✅ 改进：每个改动要有**具体验证动作**（语法检查✓ / 单点测试✓ / 指标对比✓），缺哪个就明确说"这个我无法验证，需要你跑游戏"

#### 原则3：会话记忆与交接（project-butler）
> AI 跨会话失忆。用固定的"交接协议"把上下文固化到文件，而不是聊天记录。

决竞球映射：
- ✅ 已有：工作日志（每次写当日完成/待办/下一步）—— 这就是 handoff
- ⚠️ 缺：**会话开始时的"接续协议"**（现在是你说"读日志"，可固化成 skill 自动做）

#### 原则4：单一事实源 skill（skill-based-architecture）
> 项目规则散在脑子里会漂移。固化成 skill 文件，每次任务前 agent 必读。

决竞球映射：
- ✅ 已有：`.pi/skills/` 4 个 skill（battle-ball / bug_fix / new_project / write_log）
- ⚠️ 缺：**"改动纪律"skill**——把"每轮只修1个根因、最多改3文件、改完必查语法"等 bug_fix 已有的规则强化执行

#### 原则5：清晰提示 + 独立 chat + 重置上下文（awesome-vibe-coding）
> 模糊指令→幻觉。每个独立任务开新对话，混淆了就重置。

决竞球映射：
- ✅ 现在做的好：每个任务基本独立
- 💡 建议：大改动（如 P0/P1）用"先复述+纲要确认再动手"的协议（battle-ball skill 已有，**要严格执行**）

#### 原则6：迭代纪律（loppety）
> 快速迭代≠乱改。小步快跑，每步可回退。

决竞球映射：
- ✅ 已有：每个改动控制在 1-3 文件
- 💡 建议：**每个逻辑改动后 git commit**（现在堆积多改动才提交，回退困难）

## 三、针对决竞球的改进方案（按性价比排序）

### 🥇 方案A：自动模拟比赛 + 指标统计（治本，强烈推荐）

**解决**：根除"必须手动跑游戏验证"——改完代码我自动跑10场，看指标有没有回归。

**做什么**：
1. `battle_manager` 支持 headless 自动开始（跳过备战面板点击）
2. 加 `match_stats.gd` 统计：传球成功率 / 外场接球率 / 卡死次数 / 状态切换频率 / 得分 / 时长
3. 跑 N 场输出 CSV/JSON 报告

**指标设计**（直接对应已知痛点）：
| 指标 | 防什么回归 |
|---|---|
| 传球成功率（队友接住/总传球） | 接球 bug |
| 外场接球率 | 外场接不到队友传球 |
| 卡死次数（stuck_timer 触发） | P0 卡线 |
| 状态切换频率（state/sec） | 抖动 |
| 双方得分差 | 整体平衡 |

**收益**：我改完→我跑10场→指标OK再交付。你只验证"手感对不对"这种我没法量化的事。

**成本**：中等（改 battle_manager + 新建 stats 脚本，约 2-3 文件）

---

### 🥈 方案B：关键函数单元测试（治标，快速见效）

**解决**：减少低级逻辑 bug。像 P1 验证 `_curve` 曲线那样，改完函数我自己先验输出。

**做什么**：
- 新建 `tests/ai_unit_tests.gd`，headless 跑
- 覆盖：`_curve`（4种曲线边界值）/ `_utility_catch`（队友球vs敌方球）/ `_ball_in_reachable_half` / `_is_role_taken_by_other` 这类纯函数
- 每个 AI 改动后我自动跑一遍

**收益**：抓住逻辑错（如 P1 的曲线数学错），抓不住整体行为（需方案A）。

**成本**：低（新建1文件，覆盖已有纯函数）

---

### 🥉 方案C：回归基线（防"改 A 坏 B"）

**解决**：建立"正常比赛"的事件序列基线，每次改完对比有无偏离。

**做什么**：
- 记录一场正常比赛的关键事件流（每秒：球位置/持球者/各AI状态）到 JSON
- 改完后跑同样种子，diff 事件流
- 偏离超过阈值 → 警告

**收益**：P0 修好后被 P1 弄坏能立刻发现。

**成本**：中（依赖方案A的模拟基础设施）

---

### 🏅 方案D：强化协作纪律（零成本，立即生效）

**解决**：减少来回次数，不引入新代码。

**做什么**（固化为 skill 或对话约定）：
1. **我自检升级**：每个改动除了语法检查，尽量跑方案B的单测；跑不了的明确说"需要你验证 X"
2. **批量交付**：攒一个小批次的改动一起自测，而不是改一行就让你测
3. **风险自评**：每次改动我标注"风险等级"（tiny-fix/quick-win/feature），高风险的必须配验证
4. **git 小步提交**：每个逻辑改动 commit 一次，方便回退

**收益**：立竿见影减少你的测试负担。

**成本**：零（纯流程改进）

## 四、落地建议（我的推荐路径）

```
第1步（立即）：方案D（协作纪律）+ 方案B（关键函数单测）
  ↓ 零/低成本，马上见效，先止血
第2步（本周）：方案A（自动模拟比赛+指标）
  ↓ 投入中等，但根治"手动测试"瓶颈，后面所有改动受益
第3步（按需）：方案C（回归基线）
  ↓ 依赖方案A，等 AI 行为稳定后再建基线
```

**关键判断**：方案A 是杠杆点。一旦能自动跑比赛+出指标，整个开发模式从"你测我改"变成"我自测+你验手感"，效率提升最大。

## 五、已有的好习惯（继续保持）

这些决竞球已经在做，是 vibecoding 的优秀实践，**不要丢**：

- ✅ 工作日志（= project-butler 的 handoff 机制）

- ✅ battle-ball skill 的"先复述+纲要确认"（= 清晰提示原则）
- ✅ bug_fix skill 的"每轮1根因/最多3文件"（= 小步快跑）
- ✅ 改完查语法（= 无证据不算完 的雏形）

**缺的主要是"自动验证"这一环**（方案A/B/C）。
