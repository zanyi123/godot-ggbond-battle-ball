# 副系统方案：事件触发-响应系统（2026-09-11）

> 归属：副系统（离散系统）下第一个正式子系统。本文回答：五点内容在代码文件结构中的实现方式——**集中集成还是分散**（不含接口签名等必要内容）。
> 现状调研基于 2026-09-11 代码实况。

## 一、架构决策：轻量事件总线（集中分发）+ 响应器（分散实现）

**结论：一个新文件（事件总线），其余全部分散进既有归属地。**

推理：
- 天赋、被动、元素克制、未来副系统都要在"命中/伤害/球权/冷却结束"这些**同一批判定点**插入逻辑。若各自分散侵入，`take_damage`/`ball.gd` 会被 N 处侵入，主逻辑被打散（违背副系统规范"挂接点唯一"）。
- 若把响应逻辑也集中（全部塞进总线文件），违背单文件单职责，且韧性等已内嵌且工作良好的判定要被迫搬迁。
- 因此：**主逻辑判定点只负责 emit 事件（一处一行）**；各副系统作为**响应器在自己文件里**订阅事件、实现自己的响应逻辑。新增副系统 = 新文件 + 订阅，主逻辑零改动。

```
主逻辑判定点（take_damage / ball.gd / battle_manager）
  │  emit(event, payload)   ← 每个判定点只加这一行
  ▼
EventBus（唯一新文件，事件枚举 + emit/subscribe）
  │  分发给订阅者
  ├── TalentSystem（天赋响应器）
  ├── SpiritSkillTrigger 被动响应器（既有文件内扩展）
  └── 未来副系统……
```

## 二、五点逐点方案（现状 → 实现位置 → 集中/分散）

### 点1：防御时韧性系统生效 —— 【已实现，保持分散，仅加 1 行 emit】

- 现状：`player.gd::take_damage` 内 `is_ready_to_catch` 分支（韧性衰减 + 四种效果 roll）已完整工作；`ball.gd` 消费端已修（knockback1=接住拿球权）。
- 做法：**不搬**。仅在 take_damage 末尾 emit `HIT_TAKEN {attacker, defender, damage, effect, was_ready_to_catch}`——供天赋/被动/未来系统监听。
- 集中/分散：**分散（原地内嵌）**。韧性是受击语义的一部分，拆出去反而破坏 take_damage 的自包含性。

### 点2：天赋树（大厅点亮 + 对局生效）—— 【新文件集中子系统 + 数据文件】

- 现状：角色天赋只有**展示字段**（`player.gd:202-203` talent_name/talent_desc，从 characters.json 读），零逻辑生效（"不屈意志：体力<30% 攻+15%"未实现）；天赋树（大厅点亮型）不存在，无数据文件。
- 实现位置：
  - **数据**：`data/systems/talent_tree/tree.json`（节点：id/名称/前置节点/效果类型/数值/技能解锁）
  - **对局侧逻辑**：`scripts/systems/talent/talent_system.gd`（响应器，订阅事件总线）
    - 属性类天赋（如"攻+15%"）→ 挂 `refresh_bonuses` 管道（与训练/营养/装备同模式，返回 bonus 字典）
    - 事件类天赋（如"接球成功后下次投球+X"）→ 订阅 `BALL_CAUGHT` 等事件，改写自身状态
  - **大厅侧**：点亮 UI + 存档（PlayerSaveManager 扩展 `get_talent_tree/save_talent_tree`）——大厅 UI 归 UI 层，本方案只定逻辑与数据
  - **天赋给技能（主动/被动）**：**复用元灵技能体系，不单独做**（主人明确）——天赋解锁的技能直接写入 `player.equipped_skills`，走 spirit_system 既有触发链；天赋系统只负责"解锁资格"，不重复实现技能效果
- 集中/分散：**集中成独立子系统**（talent 目录：逻辑+数据），通过事件总线和 bonuses 管道两个标准挂接点接入，主逻辑不感知天赋存在。

### 点3：被动技能系统修复+优化 —— 【分散进 spirit_skill_trigger.gd，不新建文件】

实现位置（全部在 `scripts/systems/spirit_system/spirit_skill_trigger.gd` 内，分散改）：
1. **type 分支**：`trigger_skill` 开头检查 `skill_data.type == "passive"` → 直接 return false（禁止主动/手动释放）——机制修复
2. **被动自动触发**：新增 `_on_event(event, payload)` 响应器注册到事件总线——按被动技能的**触发条件**（事件类型）自动调用内部触发路径（跳过"手动释放"检查，仍走冷却+能量校验）；冷却结束即满足再次触发的条件之一

# 执行级落地方案（2026-09-11 第二版：每点到函数/行级）

## EventBus 落地（全案前置）

**新文件** `scripts/systems/event_bus/event_bus.gd`：
```gdscript
class_name BattleEventBus
extends Node
enum GameEvent { HIT_TAKEN, BALL_CAUGHT, BALL_LAUNCHED, PLAYER_DEFEATED,
                 SCORE_CHANGED, COOLDOWN_READY, STAMINA_THRESHOLD,
                 MATCH_PHASE_CHANGED, COUNTER_HIT }
var _listeners: Dictionary = {}   # GameEvent -> Array[Callable]
func emit_event(ev: GameEvent, payload: Dictionary) -> void:
    for fn in _listeners.get(ev, []):
        if is_instance_valid(fn.get_object()): fn.call(payload)
func subscribe(ev: GameEvent, fn: Callable) -> void:
    if not _listeners.has(ev): _listeners[ev] = []
    if not fn in _listeners[ev]: _listeners[ev].append(fn)
func unsubscribe(ev: GameEvent, fn: Callable) -> void: ...
```
**注册方式**：`add_to_group("battle_event_bus")`——任何节点 `get_tree().get_first_node_in_group("battle_event_bus")` 取用，免逐层注入。
**创建**：battle_manager `_ready` 首行创建 + 入组（3 行）；结算/回菜单随场景销毁（子节点，无泄漏）。

# 第三版修正（2026-09-11）：被动触发语义纠正 + 天赋树四方向设计 + 拓展审视

## 一、点3 语义纠正：被动 = 事件条件触发（不是 CD 循环自动放）

上版"CD 好+能量够就自动放"理解有误，纠正：**被动技能必须满足配置的触发事件才释放**。

**被动技能数据结构扩展**（skills.json 的 passive 项新增 trigger 字段）：
```json
{ "id": "skill_大地_2", "type": "passive",
  "trigger": { "event": "HIT_TAKEN", "condition": {"field": "defender", "op": "is_self"} },
  "cooldown": 10.0, "energy_cost": 10,
  "tags": ["player_def_up_flat"], "tag_params": {"player_def_up_flat": {"duration": 3.0, "value": 30.0}} }
```
**触发机制**（spirit_skill_trigger 内，响应器模式）：
- `set_player_skills` 时：passive 技能按 `trigger.event` 向 EventBus 订阅
- 事件到达 → 检查 condition（首期支持 {field, op, value} 简单比较，payload 字段）→ 检查 CD（>0 跳过）→ 检查能量（不足跳过，等下次事件）→ `_fire_skill`
- **CD 语义 = 触发后的内冷却**（防同一事件流连续触发）；**能量语义 = 触发消耗**
- **旧数据兼容**：无 trigger 字段的 passive 不自动触发 + push_warning("被动缺少触发条件配置")——没有条件就不该乱触发（技能_大地_2 需补 trigger，建议 HIT_TAKEN/自受击，最终主人定）

## 二、点2 天赋树：四方向 + 三类天赋点（与被动技能标签同构）

**主人设计**：四方向（进攻/生存/防御/增益）；天赋点类型"很像被动技能标签的形式"，三类：
- **event（事件触发）**：订阅事件（可关联其他离散系统，如 COUNTER_HIT=元素克制命中）→ 执行 tags
- **passive_global（全局生效被动）**：常驻
- **manual（手动触发）**：天赋给主动技能 → 进 equipped_skills 走元灵触发链（不单独做）

**数据结构**（tree.json，与技能 tag 同构）：
```json
{ "directions": ["进攻", "生存", "防御", "增益"],
  "nodes": [
    {"id":"atk_1","direction":"进攻","name":"弱点洞察","requires":[],"cost":1,
     "type":"event","event":"COUNTER_HIT",
     "tags":["ball_dmg_up_flat"],"tag_params":{"ball_dmg_up_flat":{"duration":5.0,"value":10}}},
    {"id":"sur_1","direction":"生存","name":"坚韧体魄","requires":[],"cost":1,
     "type":"passive_global","tags":["player_max_hp_up_flat"],"tag_params":{"player_max_hp_up_flat":{"value":20}}},
    {"id":"def_1","direction":"防御","name":"手动铁壁","requires":[],"cost":2,
     "type":"manual","skill_id":"skill_大地_2"} ]}
```

**关键架构简化（同构复用）**：天赋点 event/manual 型与被动技能**结构完全同构**（trigger+tags+tag_params+cooldown+energy）→ **共用同一个执行器**（订阅→条件→CD/能量检查→调 SpiritTagEffectHandler 执行 tags）。天赋系统只做：点亮存档/资格校验/注册响应器，**效果执行零新代码**——"不单独做"落到处。

**全局被动的两条实现路径**：
- 数值型（max_hp/attack 类）→ **bonuses 管道**（refresh_bonuses 时读 TalentSystem，与训练/营养同模式，常驻干净）
- 效果型（开局护盾类）→ 开赛一次性 apply tags（duration=整场时长）

## 三、拓展审视：本设计的不合理处（5 条，待主人拍板）

1. **能量竞争冲突**：被动/事件型天赋自动触发**与玩家主动技能共用同一能量池**——被动后台自动扣能量会抽干玩家想留的大招能量。候选解：① 被动触发设能量保留线（energy 不扣到 X 以下）② 被动不耗能量只吃 CD ③ 分池。**需主人定**。
2. **tag 效果叠加风险**：高频事件（HIT_TAKEN 每次命中都发）反复触发同一 tags——若 handler 的 buff 是叠加语义会无限叠攻。需确认 `_apply_player_stat_buff` 是"刷新"还是"叠加"语义；若是叠加，响应器执行前需去重/刷新强制。**实施时必须核实**。
3. **天赋点数经济未定义**：cost 字段有了，但点数来源（升级？成就？）、每方向上限、重置规则（免费/花费）未定——**待主人**。无经济限制=四树全点，方向设计失去意义。
4. **sim 模式天赋策略**：AI 对局的天赋配置（全不点/默认模板/随机）会改变基线——需定义 sim 默认（建议：sim 强制不带天赋=与现有基线连续）。
5. **触发条件的表达能力边界**：首期 condition 仅支持 {field, op, value} 简单比较（payload 字段/球员状态）——复杂条件（"队友持球且敌方半场"）需要组合表达式，首期不做，遇到先绕。明确边界防止后续硬塞。

## 四、修正后的实施顺序

1. EventBus（不变）→ 2. 被动修复 v2（type 禁主动 + trigger 订阅 + 能量 + 同步锁；skill_大地_2 补 trigger 数据）→ 3. 元素克制（不变）→ 4. 韧性 emit（不变）→ 5. 天赋树（数据结构+TalentSystem 响应器+存档；大厅 UI 另立）→ 6. 审计（不变）

## 一、事件类型登记表（v1 首期 10 个）

**设计原则（开发者思维）**：

- **双轨合一**：ball/GameManager/player 已有大量 Godot 信号（ball_caught 等）——EventBus 初始化时**接线转发既有信号**，订阅者只看 EventBus 一处，不做双轨

- **持久化**：EventBus 设 `log_enabled`——事件流全量写入比赛日志（挂 match_stats），副系统的作用可量化回溯（"本场弹飞 X 次/天赋触发 Y 次"），服务调参与平衡分析

| # | 事件 | 触发点（来源） | payload | 首期订阅者 | 来源方式 |
|---|---|---|---|---|---|
| 1 | BALL_LAUNCHED | ball.launch() 末尾 | {attacker, direction, damage, max_dist} | 统计/天赋 | 新 emit |
| 2 | BALL_HIT_TAKEN | ball._on_body_entered 命中段 | {attacker, defender, damage, effect, was_ready_to_catch} | 天赋(event型)/被动/统计 | 新 emit |
| 3 | BALL_CAUGHT | 转发既有 ball_caught 信号 | {player} | 统计/天赋 | 信号转发 |
| 4 | BALL_BOUNCED | ball 弹飞分支（bounced=true 处） | {defender, direction} | 统计/天赋 | 新 emit |
| 5 | BALL_OUT_OF_FIELD | 转发既有 ball_out_of_bounds | {pos} | 统计 | 信号转发 |
| 6 | PLAYER_DEFEATED | 转发既有 player.defeated | {player, last_hit_by} | 天赋/统计 | 信号转发 |

# 第六版修正（2026-09-11）：作用域限定正式对局玩法事件
