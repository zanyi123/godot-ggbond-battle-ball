## 一、起点：发现痛点（2026-06-17）

### 触发事件
开发 AI 系统时进入循环：**我改代码 → 主人手动跑游戏测试 → 发现 bug → 反馈 → 我修 → 再测**。

典型例子：P0 修了卡死，又冒出"主攻手抢球"；修了抢球，又冒出"职位绑死无法切换"；修了切换，又冒出"双队单人卡线"；修了卡线，又冒出"外场接不到队友传球"……

每个改动都要主人当人肉 QA 验证，**测试效率极慢**，主人明确表达"有点难受"。

### 根因诊断
- **不是提示词问题**：battle-ball / bug_fix skill 的规则已经够细
- **不是上下文问题**：工作日志已经在做 handoff
- **是缺"自动验证"这一环**：AI 行为改动只能靠肉眼跑游戏验证

### 关键认知
> Vibecoding 的效率瓶颈往往不在"AI 写代码"，而在"AI 不知道自己写的对不对"。
> 没有自动验证手段，人类就变成 AI 的测试员，这是反模式。

## 三、改进方案确立（2026-06-17）

### 四个方案（性价比排序）
- **A 自动模拟比赛+指标统计**：根治"手动测试"（杠杆点）
- **B 关键函数单测**：减少低级逻辑 bug
- **C 回归基线**：防"改 A 坏 B"
- **D 协作纪律**：零成本减少来回

### 决策
主人决定：**先做方案 A**（根治瓶颈），后续按需补 B/C/D。

### 目标状态
```
现在：我改 → 主人测 → 反馈 → 我修
目标：我改 → 我自动跑N场看指标 → 指标OK再交付 → 主人只验"手感"
```

### 2026-06-17：方案A 首次发力——暴露并修复初始球权僵死 bug
**事件**：方案A 跑通后，跑3场立刻发现 2/3 场比分 0-0、0 传球 0 投球 0 击中。

**根因**：`_assign_initial_ball` 把初始球分给 `team_a_players[0]`，而该位是 `input_mgr` 的**玩家控制位**。sim 模式无人按键→持球人永远不动→全场僵死。肉眼单场测试可能刚好抽到正常的场（球分给队B），根本发现不了这个 50% 概率 bug。

**修复**：sim 模式下初始球分给 AI 队友（位置2）。

**验证**：修复后 3 场全部打起来（2-3、2-1），击中 7-10 次，传球率 100%。

### 💡 这次事件证明了什么
> **“自动模拟”的价值不是“更快”，而是“看到肉眼看不到的系统性问题”。**
>
> 50% 概率僵死的 bug，肉眼测试需要跑很多场才能发现（而且你会以为“这局没打起来是随机性”）。方案A 跑3场就抓到了。
>
> 这是“我改→我跑→我修”闭环的首次完整跑通：
> - 发现问题（跑模拟看指标）
> - 定位根因（看AI日志）
> - 修复（改代码）
> - 验证（重跑模拟对比）
>
> **主人一次都没跑游戏，我把 bug 找了并修了。** 这就是方案A 的杠杆价值。

## 七、他山之石（值得反复读的引用）

### "无证据不算完成"（agentic-os）
> AI 最爱说"改完了"，但"done"必须有可验证证据，不能靠自报。
> 决竞球映射：每个改动要标注"语法✓ / 单测✓ / 指标✓"，缺哪个明说。

### "评估先行，选最小工作流"（agent-workflow-kit）
> 不是所有改动都要走完整流程。先评估风险，选最小够用的。
> 决竞球映射：tiny-fix 改配置不用全套，feature 重构必须配验证。

### "AI 协作的瓶颈在验证，不在生成"
> 本次调研最核心的认知。决竞球的全部痛点都指向这一点。
