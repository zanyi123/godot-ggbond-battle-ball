# 决竞球 (Battle Ball) 项目开发技能

本技能用于规范「决竞球 Battle Ball」Godot 项目的 AI 辅助开发流程。

## 核心工作原则

### 1. 消歧义 + 强制复述审核
收到用户消息后，**必须执行以下两步，缺一不可**：

**第一步：消歧义**
- 先思考是否存在歧义或不明确之处
- 如果有歧义，**必须先提问确认**，不要猜测后直接执行
- 如果需求清晰无歧义，进入第二步

**第二步：强制详细复述 + 等待审核（修复/修改类任务必须执行）**
- **无论需求是否清晰，只要涉及修复 Bug、修改代码、调整逻辑、变更行为，都必须先详细复述**
- 复述内容必须包含：
  1. 问题现象（用户描述的具体表现）
  2. 初步定位的根因（为什么会出现这个问题）
  3. 计划修改的文件清单（精确到文件名）
  4. 每个文件的具体改动点（改什么、怎么改）
  5. 预期修复后的效果
- 复述完成后**必须停下，等用户手动确认「同意/可以/开始」后才能动手修改**
- ❌ 禁止复述完直接开始修改，必须等用户审核通过
- 新增功能/新建文件类任务可简化复述，但仍需纲要确认

### 2. 复述与纲要
回答时**必须先做两件事**：
- **复述理解**：用简短的话重述用户的需求，确认双方理解一致
- **给出纲要**：列出解决问题/实现功能的步骤大纲，让用户心中有数

### 3. 过程精简
- 解决问题的**详细过程不要全部显示在对话框里**（如大量的中间文件内容、逐步调试日志等）
- 只展示关键节点和关键决策
- 需要用户确认的重要节点除外

### 4. 完成总结
每项工作完成后，**必须总结**：
- 做了什么（完成了哪些要点）
- 改动涉及哪些文件
- 是否有待后续处理的事项

### 5. 自检自测（含强制语法自检）

**每次修改任何代码/场景文件后，必须先执行语法自检，全部通过才能交付。**

#### 5.1 C# / Unity 项目强制检查项
- **括号匹配**：`{}` `()` `[]` 数量必须相等
- **API 存在性**：调用的每个类/方法/字段必须在目标文件中实际存在（用 `Select-String` 验证）
- **命名空间引用**：`using` 的命名空间必须在 asmdef 引用范围内
- **场景文件 .unity**：
  - 必须以 LF 换行符结尾（末尾字节必须是 10）
  - YAML 格式 `key: value` 冒号后必须有空格
  - GUID 必须与对应 .cs.meta 文件一致
- **编译验证**：有条件时用 Unity 编译，无条件时必须完成上述静态检查

#### 5.2 GDScript / Godot 项目强制检查项
- **语法检查**：`godot --check-only --no-window`
- **括号匹配**：`func`/`end`、`if`/`endif` 配对
- **节点路径**：`$Node/Path` 必须与场景树一致

#### 5.3 功能自测
- **实现后必须自检**：检查代码逻辑、节点引用、信号连接等是否正确
- **必须进行可运行的测试**：通过运行场景、打印日志等方式验证功能
- 如果发现自测无法覆盖（如需要手动操作验证），**明确告知用户需要手动验证的内容**

### 6. 有疑问就问
- 遇到不确定的设计决策、数值设定、交互方式等，**主动提问**，不要自行假设
- 宁可多问一句，也不要做错返工

### 7. 称呼
- 回复开头加「主人」

## 开发规范

- 遵循 Godot 4 最佳实践（场景化设计、信号驱动、节点组合优于继承）
- 代码需有清晰的中文或英文注释
- 变量/函数命名遵循 GDScript 风格指南（snake_case）
- 合理组织项目目录结构

### 通用规则 1：文件命名纪律（2026-09-25 主人定）

- 在工作文件夹里创建新文件，命名**必须与当前所执行的任务高度切合、能概括内容**，且**方便管理与识别**
- 禁止浮夸命名（大而空的标题词、与内容不符的修饰性命名）
- 判定标准：仅看文件名即可判断该文件属于哪项任务、大致内容是什么

### 通用规则 1.5：工单纪律（2026-09-30 主人定，每个工单开头必须含）

1. **工单作业流程线**：工单开头必须标注一份**随工作顺序排列的任务清单，每项任务标注对应负责窗口**——主人拿这条线直接追进度
   - 格式：`任务序号. 任务名 → 负责窗口 → 完成标记（⬜待做/🔨进行中/✅完成+commit）`
   - 任务完成时**当次更新**流程线标记，不得滞后
2. **完成即写进度看板**：领取任务完成后，必须**立即**在进度看板登记（状态/commit/日期）——先看板后收工，漏写=没交付
3. **待决策自动双汇报**：工单执行中产生"需主人定夺/选择/裁决"的内容时，除看板登记外，**必须自动同步写入工单所在文件夹下的决策清单**（如《元灵技能AI规划/待主人决策.md》《技能规划/待主人决策.md》——按【窗口名-月日-序号】格式，两三行人话+推荐）——写工单不写决策清单=没交付
4. **决策清单并发写保护（2026-09-30 主人事故教训：编辑器缓存覆盖丢登记）**：
   - 写决策清单**必须"读最新→追加→存"三步一气呵成**（脚本/工具内完成），禁止凭记忆或旧编辑器缓存改写整文件
   - **只追加不重排**：不改他人条目、不移动已定夺行（移档由规划窗口统一做）
   - 改完立即 commit（决策清单是最高频提交对象）；发现内容与预期不符=立即停手上报，不得用本地旧版覆盖
   - 恢复通道：git 历史 + 工作日志 + 规划窗口会话三方可交叉找回
5. 以上条款适用于所有工单（含框架单的子单卡）；决策清单分轨各自唯一、互不混写

### 通用规则 2：代码层设计三考量（2026-09-25 主人定，涉及设计与详细代码落实时必查）

落实详细工作的代码层时，必须基于以下三方面综合考量后再动手：

1. **安全性（兼容优先）**：改动必须兼容既有代码与后续工作的搭建，不得引入与后续规划冲突、会导致严重报错的实现（如破坏接口签名、占用未来规划的字段/路径、硬编码阻碍扩展）
2. **高效性（一次过）**：以"测试一次通过、不返工"为目标设计——动手前先核对接口/参数/调用链真实存在，禁止"先写再试错多轮返工"
3. **简洁性（代码量）**：在满足功能前提下代码量最小化——复用既有机制，不重复造轮子，不写冗余分支

三方面冲突时的取舍顺序：**安全性 > 高效性 > 简洁性**（宁多写代码保兼容，不图简洁埋雷）

## 3D 模型缩放铁律（2026-08-10 确立）

### 核心规则
`player_3d_test.gd` 第 810 行的 FBX 缩放**必须为 1.0**，不准更改：

```gdscript
# 第 810 行: FBX 缩放强制为 1.0，禁止添加任何补偿
if idle_inst is Node3D:
    idle_inst.scale = Vector3(1.0, 1.0, 1.0)  # 固定值，不准改
```

### 规则原因
- FBX 原始尺寸虽然小（AABB size.y ≈ 0.011），但通过上层 ModelSlot 的 `scale=70` 已能正确放大
- 额外的 65 倍补偿会导致模型过大，遮挡球场视野

### 缩放层级关系
```
ModelSlot (scale=70) ← 唯一缩放控制点
  └── idle FBX (scale=1.0) ← 强制 1.0，禁止修改
```

### 禁止行为
- ❌ 禁止在 idle FBX 上添加任何 scale 补偿（65、70 等）
- ❌ 禁止修改 `Vector3(1.0, 1.0, 1.0)` 的值
- ❌ 禁止添加 "AABB 小于 0.1 则自动补偿" 之类的动态缩放逻辑

## 3D 场景单位制铁律（2026-09-10 确立）

### 核心规则
3D 层世界单位 = **GD 2D 像素，1:1，零换算**。同步坐标只做 `(x, y) → (x, 0, y)`。
**禁止**在 3D 层引入米制换算因子（×0.01 / ×0.02 是 Unity 侧历史，不进 Godot）。读 Unity 数值时 ×50（角度不变）。

### 定死规格表（硬性基准，禁止改动）
| 项 | 定死值 | 来源 |
|---|---|---|
| 球员缩放 | ModelSlot scale=70（唯一控制点），FBX scale=1.0 | 2026-08-10 铁律 |
| 球员模型高度 | ≈49.86 | player_3d_test 实测 |
| 球缩放 | BALL_SCALE_3D=30（以 player_3d_test 一体化平台为准） | player_3d_test |
| 球高度 | 持球 55 / 飞行 30 | player_3d_test |
| 球自旋 | 12 rad/s | player_3d_test / Unity 同源 |
| 相机 | TOP_Y=1000 / ORTHO_SIZE=870 / ANGLED_DIST=1200 / FOV=62 | player_3d_test 大相机 |
| 球场 GLB | battle_field_3d_yup.glb scale=1（原生即像素级）+ 根偏移(-1.837, 1.042, 0.355) 微调 | battle_field_3d_test.tscn |
| 场地判定常量 | 唯一权威 = field_zone.gd 像素值（内场 ±380/±260、外场 ±510/±325、中圈 60） | 2D 玩法层 |

### 推导顺序（不可倒置）
球员规格（定死）→ 单位=像素（定死）→ 球场模型比例由"白线必须落在 field_zone.gd 权威常量"反推（画框校准）→ Unity 场景数值只作观感参考（×50 读取）。

```

  → 第二步：强制详细复述（现象+根因+文件清单+改动点+预期效果）
```

- ❌ RectTransform 不设 anchor/pivot（必须显式设置）
