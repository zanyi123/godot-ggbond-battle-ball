# 多人合击仪式型拓展构思

> 提出人：主人（2026-10-01）｜记录窗口：内容优化架构设计窗口
> 状态：**构思已汇报，五个决策点待主人拍板，未出工单未派工**
> 核心句：给现有两套"条件到立刻成"的合击机制，加第三种**仪式型**形态——发动后先摆架势（固定站位+蓄力），事件扳机齐了技能才真正出手。

## 一、为什么做

主人构思：合击不该是"能量够了两边自动放"，应该有协作的仪式感。例：二人合击技，使用时双方要在场上固定站位蓄力，有技能事件触发特定动作才能发出技能。实现路线倾向：把合击包装成一个技能，靠**技能标签 + 事件-响应系统**挂条件。

## 二、现状：合击已有两种形态（都是"条件到立刻成"）

| 形态 | 机制 | 释放条件 | 缺什么 |
|---|---|---|---|
| **半装配对型**（工单12 S1 OP_COMBO，两人合体放坦克） | 两人各持半技能登记（player_combo_ready 标签）→ skill_state_manager 配对 | 同队互补 role + 双方存活 + 距离 ≤150px 自动合体，合体期倒计时到期拆分 | 无站位、无蓄力、无事件扳机 |
| **同窗爆发型**（11框架 team_combo_tracker，三人合击增益） | 监听 skill_used 登记 → 12s 窗口内 distinct 施法者按 role 计数达标 | 计数够自动成立 → on_formed 标签结算 | 同上 |

本构思 = **第三种：仪式型（setup_ritual）**。落点：team_combos.json 合击定义表新增一种触发模式，站位点/蓄力时长/释放事件/打断规则全配在表里，不动技能本身——即主人说的"包装好多人技能后面挂它"。

## 三、拓展后的完整链路

```
main 满足首发条件（能量+技能就绪）
  → ① 邀约：通知队友"准备合击"（tracker 二期挂点已预留，COMBO_SETUP 协议位现成）
  → ② 跑位：各成员跑向场上指定站位点
  → ③ 蓄力：全员到位后原地站桩蓄力 N 秒（累积秒计时，确定性纪律）
  → ④ 扳机：释放事件发生 → 技能真正出手
  → ⑤ 结算：走既有标签流落地效果
  ✗ 失败面：邀约后超时没到位 / 蓄力中被击 → 合击流产
```

## 五·补、事件-响应系统对接细节（主人令细化，2026-10-01）

### 0. bus 真实机制（设计依据，均已读源码核实）

- **创建**：battle_manager.gd:155-160 比赛初始化时 `Node.new()+set_script` 建 bus，`add_to_group("battle_event_bus")`，随后 `wire_sources(ball, players)` 把既有 Godot 信号（ball_caught→DEFEND_CAUGHT、defeated→HIT_DEFEATED）转发进总线；sim 模式自动开事件账本落盘 eventlog。
- **获取**：`BattleEventBus.get_bus(get_tree())` 按 group 查找（免逐层注入）。
- **派发**：`emit_event(ev, payload)` 是**同步派发**——遍历 listeners 逐个 `fn.call(payload)`，在发射点调用栈内当场执行（如 HIT_TAKEN 在 ball.gd:566 命中结算中途回调就到了）。
- **订阅**：`subscribe(ev, fn)` 内部 `if not fn in` 防重复；`unsubscribe(ev, fn)` 按 Callable 精确退订。
- **发射点现状**（生产）：HIT_TAKEN=ball.gd:566 / DEFEND_BOUNCED=ball.gd:609 / ATTACK_LAUNCHED=ball.gd:809 / HIT_COUNTER=player.gd:1217 / HIT_RESILIENCE_ROLLED=player.gd:1242 / DEFEND_CATCH_STANCE=player.gd:2433 / ACTION_JUMPED=player.gd:1078 / SKILL_COPIED=player_route.gd:144 / RESOURCE_COOLDOWN_READY=spirit_skill_trigger.gd:607 / HIT_DEFEATED·DEFEND_CAUGHT=bus wire 转发。

### 1. 总原则：事件是"即时快报"，状态机是"固定步长裁定"

bus 回调是同步派发（可能发生在球命中结算、buff 结算的调用栈中途），因此回调里**只做轻量登记（置 flag / 入凭证槽），不做状态转移、不做效果结算**；状态机推进全部在 tracker 的 0.2s 固定步长 `_process` 里消费 flag。这正是 event_hooks 已验证的模式（受击置 until_cycle，查询时消费）——保证确定性纪律，sim 逐位一致可守。

### 2. 三个对接面

**面A：到位判定 = 周期轮询，不走事件**
- bus 没有"到达"事件，也不新增（到达是 AI 移动状态机内部转移，为它加对外发射点侵入面大）。
- tracker 每 0.2s 判各成员与站位点距离 ≤ arrive_radius。先例=OP_COMBO pair_compatible 距离判定。
- 阈值下限约束：0.2s 内成员最多位移 ≈ 速度×0.2（数百 px/s → 数十 px），故 **arrive_radius ≥ 40px** 才不会跨周期漏判"到达又离开"。

**面B：打断与流产 = 订阅 HIT_TAKEN + HIT_DEFEATED（按需订阅）**
- 进入仪式态（存在进行中的 setup）才 `subscribe`，仪式结束/流产 `unsubscribe`——平时零订阅零开销；bus.subscribe 自带防重复，订阅侧再加幂等守卫双保险。
- `HIT_TAKEN` payload `{attacker, defender, damage, effect, was_ready_to_catch}`：defender ∈ 仪式成员表 → 置 interrupt_flag（回调内不改状态）。
- `HIT_DEFEATED` payload `{player, last_hit_by}`：player ∈ 成员表 → 置 abort_flag（人没了直接流产，优先级高于打断规则）。
- 下一个固定步长 tick 统一消费：interrupt_flag → 按打断规则（决策点1，推荐=蓄力进度减半）执行；abort_flag → 清仪式退能量（决策点3）。

**面C：释放扳机 = 一期纯周期判定；事件型扳机=订阅+凭证槽（二期扩展位）**
- 一期 `release_event: "channel_done"`：零订阅，纯周期判定（全员到位 && channel_progress ≥ channel_seconds → 释放）。
- 二期事件型：schema 配 bus 事件名字符串数组（如 `["DEFEND_CAUGHT"]`），tracker 启仪式时按 `GameEvent.keys().find(名)` 转枚举逐个订阅（未知事件名 fail-closed 拒载该条并 log）。
- 事件语义=**"允许释放的凭证"，不是直接释放**：事件到来置凭证槽（TTL=若干决策周期，event_hooks COPY_SNAPSHOT_TTL_CYCLES 先例，防凭证永存）；释放条件=蓄力满 && 凭证槽非空。事件先到蓄力未满→凭证暂存；蓄力满凭证未到→继续蓄。

### 3. 订阅生命周期与时序

- tracker 挂在 SSM 下，_ready 时 bus 可能尚未创建（bus 建于 battle_manager 初始化）——**不抢 _ready**：进入仪式态时懒获取 `get_bus(get_tree())`（仪式必发生在比赛开始后，此时 bus 必在）；取不到 fail-closed=记 log，仪式按无打断监听降级处理。
- 退订时机：释放成功 / 流产 / 比赛结束三路统一走一个 `_teardown_ritual()`，内含 unsubscribe 全量对账（订阅表先登记后订，退订按表清，防漏）。

### 4. payload 契约表（只读 payload 已声明字段，禁猜字段——第二真相禁令）

| 事件 | 生产发射点 | payload 契约字段 | 仪式用途 |
|---|---|---|---|
| HIT_TAKEN | ball.gd:566 | attacker/defender/damage/effect/was_ready_to_catch | 打断判定 |
| HIT_DEFEATED | bus wire（defeated 信号） | player/last_hit_by | 成员倒地流产 |
| 二期扳机按需 | 各处（见 §0 发射点清单） | 按 GameEvent 枚举注释 | 释放凭证 |

### 5. 确定性纪律对照表

| 项 | 做法 | 先例 |

### 6. 对接调研顺带发现的生产缺口（本窗口记录，待主人定夺是否派修）

- **STATUS_APPLIED 生产零发射**：event_hooks.WATCH_EVENTS 订阅了它（状态类反应热窗口），但生产代码无任何 emit 点，只有测试在发 → "被控反应"类 gate/钩子生产永不触发。
- **RESOURCE_ENERGY_THRESHOLD / BUFF_APPLIED 同样生产零发射**（仅测试发）。
- 影响：仪式打断若要含"被控也倒退"，需先给 status/buff 系统补生产发射点（小接线工单）；一期打断只靠 HIT_TAKEN+HIT_DEFEATED 可绕开，不被此缺口阻塞。

- **一期**：schema 扩展 + 仪式状态机 + 本地邀约 + AI 跑位 + 蓄力释放 + 流产规则。不依赖 protocol_v2；验收=平台三种子实证"站位→蓄力→出手"全链 + sim 门禁危险=0。
