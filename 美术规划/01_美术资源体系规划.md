> 建立：2026-09-19。验收铁律：**只信 Godot 实机目检**（2026-09-15 教训：Blender 数值验收≠视觉验收）。

### 线3 元灵体显示（零资产，零规划，本文档新建）
- 原作定位：元灵是实体生物（技能大量"操控元灵体与球"）；主角方 6 只：阿五(金刚)/玲珑(雷火)/冰冰(冰雪)/大山(大地)/小圣(草木)/触手怪(梦幻)；元灵之神 6 只（修罗/六叶蝗/雪鲸/赤鸠/巨石神兵/仙女龙）为元灵模式级内容。
- 用途分层：①技能释放时显现（技能表现增强）②大厅/UI 展示 ③召唤系技能实体（技能规划 S5 系统，远期）。
- 现状：建模素材库（player1~8+ball+field+actions）**无任何元灵体资产**。

**管线拍板（2026-09-19 主人确认）**：混元出 glb；元灵体**不走人形建模/绑骨流程**（官方元灵体也是非人形骨架，但我们多数场景不需要绑骨）。分层：
| 层 | 做法 | 覆盖 |
|---|---|---|
| **L1 静态显现** | 混元静态 glb + 程序运动（位移/旋转/浮动/缩放出入场）+ 光效粒子包裹 | ≈80% 技能显现（飞出/盘旋/发光/入球） |
| **L2 简单骨骼** | 2~4 骨极简链（扑翼/摆尾），Blender 手摆 | 少数特写 |
| **L3 完整绑定** | 与元灵模式/合体演出（C 类）一起立项 | 远期 |

**铁律：球员=人形管线（Mixamo 骨架绑骨吃动画库）；元灵体=显现管线（静态+程序运动不绑骨）。两条管线不混用同一验收标准。**

### 线4 动作建模（部分有基础——2026-09-19 headless 实测验证，工具 tools/probe_anim_assets.gd）
| 动作类别 | 资产 | 实测状态 |
|---|---|---|
| 待机/跑动 | avatars Idle/Jog + actions idle/jog | ✅实测：可加载、Mixamo兼容、10s/0.8s（两库内容重复） |
| 投掷/接球 | Goalie_Throw/Goalkeeper_Catch + throw/catch | ✅实测：同上，3.8s/1.3s（两库重复） |
| 防御姿态 | block_idle | ✅实测：可加载、**65骨全指版**、2.8s；**未接技能**（护盾原语#4 的表现） |
| 投球预备/接应 | pitch / receive | ✅实测：65骨全指版，3.9s/3.5s；未接入 |
| 受击反应 | — | ❌ 无资产（位移/击退有，姿势无） |
| 控制态（眩晕/定身/冰冻） | — | ❌ 无资产（状态灯有，动作无） |
| 施法手势 cast | — | ❌ 无资产（技能释放无角色动作反馈） |
| 跳跃姿势 | — | ⚠（M3 位移+影子有，空中姿势无资产） |
| 变身/元灵模式演出 | — | ❌（C 类远期） |

**实测发现（2026-09-19，探针 tools/probe_anim_assets.gd）**：
- 11 个 FBX 全部可加载、动画真实存在、全部 Mixamo 兼容（骨名带 `mixamorig_` 前缀——探针初版用裸名误判，已修正沉淀）
- **两套指骨规格混库**：8 个 33骨无指版 + 3 个 65骨全指版（block_idle/pitch/receive）。跨规格播动画：33骨动画→65骨骨架=手指静止（可用）；65骨动画→33骨骨架=手指轨道丢弃（有警告）。**后续新动作入库建议统一 33骨版**（与主角模型无指骨现状一致）
- avatars 与 actions 两库 4 组内容完全重复（Idle/idle、Jog/jog、Throw、Catch）——真正独有的新增类别=防御姿态/投球预备/接应 3 套
- **仍未验证（须目检）**：动作观感质量、与球员模型同播的表现（依赖线1 步骤③融合方案落地）
- 前提资产：Mixamo 标准骨架=跨角色动作复用的地基 ✅（检索词对照表已有 `docs/Mixamo动作搜索词对照表.md`）

## 二、资产分层模型（美术版"原语"思想）

```
配方层（量产，分钟级）——改参数不改资产
  技能特效配方（skill_vfx_config.json：一技能一行——用哪个包/哪些阶段/什么色/多大/挂哪）
  角色配色（PBR 贴图前缀 + 元素色 override_colors）
基类层（收敛，做一次）——资产本身
  模型基类：28骨人形+base网格 / 修复·杯型手·挂点工艺
  特效基类：五阶段原语（cast/projectile/impact/linger/aura）× 元素配色
  元灵体基类：主角6只（远期+元灵之神6只）
  动作基类：分类别动作库（上表现盘点）
管线层（工具链，一次性）
  模型修复流水线 tools/repair_mesh_topology.py ✅
  特效包入库流程（拷入assets→import→注册VFXEffectRegistry→配方面）❌待建
  动作导入流程（Mixamo检索→下载FBX→28骨适配→入库）⚠ 半自动（对照表有）
```

**核心账**：技能规划已证明 A 类 70 技 ≈ 10 机制族。特效同理——**10 机制族 × 6 元素配色 = 60 个配方**，多数复用同一批基类包换色（Binbun @export 换色天生支持），真正需要新建的特效基类只有机制专属那十几个（印记/护盾/领域/回旋尾迹…）。

## 四、新美术需求分流流程（三问 → 三分流）

```
Q1 资产类型？ → 模型 / 特效 / 元灵体 / 动作 / 配色
Q2 查 §三 覆盖表，基类已有？
   A 换皮复用 → 改配方参数（配色/缩放/挂点/时长）——分钟级，随技能批次走
   B 新基类   → 走对应管线（建模：生成/Blender 流水线；特效：入库注册；动作：Mixamo 检索适配）
   C 新系统   → 需新引擎机制支撑（变身状态机/合技演出相机/召唤实体）→ 与技能规划 C 类同步立项拍板
Q3 验收？ → 一律 Godot 实机目检；特效另加 headless 场景冒烟（test_3d_effect_compat 模式）
```

## 五、与技能规划的联动协议（排产配对，两边不同步就白干）

1. **A 类技能落地同批补特效配方行**：V1 主角 18 技 ↔ M2 特效首批 18 配方（先程序化轮廓过渡也行，但配方行必须建——否则技能上线无视觉反馈，欠账翻倍）。
2. **技能原语工单（分流B）必含"表现规格"字段**：五阶段取哪些、挂哪（caster/ball/impact_point/field_zone）、元素色、缩放。写进 `技能规划/02 §1.4` 的工单模板。
3. **原语↔特效基类对齐表**（首批）：护盾#4↔shield_break+magic_aura / 区域#2↔zone 粒子(ice_frost/poison_cloud) / 印记#10↔combo_ring 叠层表现 / 分裂#8↔energy_burst / 回旋↔fireball_trail / 治疗↔heal_particles / 复制系#1↔portal_vortex。
4. **C 类系统两头同步**：合技演出/变身/召唤 = 技能新系统 + 美术新机制（状态机/相机/多单位渲染），立项必须成对出现。

## 六、分期路线图（与技能 V1/V2 配套）

| 版本 | 内容 | 前置 | 预估 |
|---|---|---|---|
| **M1 模型收尾**（线1，模型窗口） | 步骤③拍板→player2 动作→8 人批量（①②④ 脚本化） | ③拍板 | 3~5 会话（另一窗口） |
| **M2 特效地基**（线2，本规划首发） | ElementColorBank 统一色表 → Binbun 接线（已知坑：projectile 漏挂脚本/SubViewport 独立 World3D 配 Environment）→ VFX-LIBRARY 挑 ~15 场景入库 → SkillVFXPlayer+skill_vfx_config 配方框架 → **V1 主角 18 技配方全覆盖** | 无硬前置（可与 V1 并行） | 2~3 会话 |
| **M3 元灵体首批**（线3） | 来源拍板（见下）→ 主角 6 只 → 技能释放显现（skill_triggered 信号挂元灵体投影，2D 权威层不动） | M2 | 1~2 会话/只（视来源） |
| **M4 动作扩展**（线4） | cast 手势 1 套 + 控制态 3 套（眩晕/定身/冰冻）+ 受击 1 套 → 状态灯/技能释放挂动作 | 步骤③（动画融合就位） | 1~2 会话 |
| **M5+ 滚动** | 队伍包美术增量（换皮为主）+ 新原语配套特效 + 元灵之神（元灵模式期） | 按需 | 随队包 |

**产能结论**：特效是"一次地基 + 永久量产"的典型（M2 后每个新技能的特效=配方一行）；元灵体是唯一需要持续建模投入的线，但主角 6 只后对手队可降级（图标/剪影）；动作靠 Mixamo 免费库成本极低。
